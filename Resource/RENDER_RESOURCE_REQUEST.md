# 그래픽 리소스 요청과 조립·텍스처 최적화 제작 계약

최신 정리: **2026-11-23 · 차세대 렌더링 최적화 기술 계획(R1~R4: EBO·정점압축·LOD·그림자 프록시·GPU 컬링/MDI·텍스처 배열) 및 v4 규모별 폴리곤 상한 개정** (선행 2026-11-22 텍스처·조립 계약 포함).
대상: 모델링·텍스처·애니메이션 제작 담당과 게임 리소스/렌더 통합 담당.
아래 최신 계약을 이후 제작의 기본으로 사용한다. 뒤의 2026-10-28~11-03 항목은 선행 요청으로 보존하며,
현재 납품·연결 상태는 최신 목록을 우선한다. 이번 갱신은 요청/설계 문서이며 v4 팩·LOD 로더·자산 납품 완료가 아니다.
[AGENTS.md](AGENTS.md)와 [POLYGON_BUDGET_ko.md](Documentation/POLYGON_BUDGET_ko.md)의 **원본 디테일 보존·규모별 폴리곤 상한(기존 v3 유지분 최대 200삼각형 / v4 최적화 적용 신규·CQ-11 자산은 7절 규모별 상한 및 LOD0~2·그림자 프록시 세트)·한도 우회 분할 금지 원칙**을 따른다.
이미 납품된 클립/모델을 다시 만들기 위한 요청이 아니다. 측정 전 임의 폴리곤 감축을 하지 않는다.

## 2026-11-23 현재 기준과 미구현 경계

- 파츠·조립 원본은 `Documentation/assembly_recipes.json`, `vehicle_assemblies.json`,
  `aircraft_assemblies.json`, `scenery_assemblies.json`, `architecture_styles.json`,
  `character_detail_assemblies.json`, `road_plan_modules.json`을 사용한다. 기존 ID·크기·접속점은 보존한다.
- 게임 렌더러(`Renderer.cpp` / `RenderQueue.cpp`)는 **2026-11-23에 OpenGL 4.5 Core / GLSL 4.50 셰이더, `std430` SSBO GPU 스키닝, `glDrawArraysInstancedBaseInstance`, `resourceId` 공유 불변 VBO 풀, VAO·3-정점 풀스크린 트라이앵글, 4 MB 링 버퍼, 프러스텀 컬링까지 1차 전환 완료**(`GAME_DOCUMENTATION.md` 52절)했다.
- 다만 `tools/pack-resources.mjs`와 `ResourceAssets.cpp`는 아직 **비인덱스 삼각형 리스트(`v3`, 252 B/삼각형)**와 정점색 샘플링 경로를 사용한다. `ResourceVertex`의 압축·인덱스 버퍼(EBO)·UV/탄젠트·LOD0~2/그림자 프록시 서브메시·GPU PBR 텍스처 배열·Hi-Z 오클루전/MDI는 **7절의 R1~R4 단계**로 구현한다.
- 원본 GLB에 텍스처를 넣거나 폴리곤을 높이는 것만으로 게임 통합이 완성되지 않으며, **v4 상향 폴리곤 상한은 R1(EBO·정점 압축) + R2(LOD·그림자 프록시) 통합과 함께 적용**한다.

### OpenGL / GLSL 개선 기준 — 사용자 추가 지시 반영

- 새 텍스처 렌더 경로의 우선 목표는 **OpenGL 4.5 Core / GLSL 4.50**이다. 텍스처 배열·UBO/SSBO·
  불변 텍스처 저장소·DSA·동기화된 버퍼 업로드를 사용할 수 있는 기준으로 잡는다.
  `gl_DrawID` 등 4.6 기능이 실제 구현에 필요하면 **OpenGL 4.6 / GLSL 4.60**으로 상향할 수 있다.
  이 버전 선택은 게임 통합 설계이며 이번 문서 작업으로 실행 파일의 요구 사양이 바뀐 것은 아니다.
- 실제 대상 GPU/드라이버의 컨텍스트 생성, 필수 함수·텍스처 크기/배열 레이어·텍스처 유닛·버퍼 한도를
  시작 시 확인하고 로그로 남긴다. 구버전 렌더러를 영구 병행하는 것을 필수 조건으로 두지 않는다.
  전환 중 한시적 경로가 필요하면 범위와 제거 시점을 기록하고 미지원 기능을 조용히 성공 처리하지 않는다.
- `#version`만 올리지 않는다. 현재 `glVertexPointer/glTexCoordPointer`, 즉시 모드/고정 기능·행렬 의존,
  실제 GL_QUADS 제출을 VAO/VBO/EBO·명시적 vertex input/행렬 버퍼·삼각형 제출로 함께 이전한다.
  월드/스킨·그림자·UI/글꼴·후처리·모델 도감·렌더 검사 경로를 같은 컨텍스트 계약으로 대조한다.
- 재질은 공통 템플릿과 버퍼의 작은 레코드, 인스턴스는 재질/배열 레이어 ID·tint·상태를 참조하도록 설계한다.
  UBO/SSBO의 std140/std430 정렬과 CPU/GPU 레코드 크기·오프셋을 검증한다.
  셰이더 변형 키는 필요한 alpha/스킨/조명 기능으로 제한하고 색상·자산 ID마다 프로그램을 만들지 않는다.
  Multi-Draw Indirect·GPU culling은 CPU 제출 병목이 확인될 때 확장하며 처음부터 모든 기능을 강제하지 않는다.
- 업로드는 불변 저장소와 PBO/버퍼 링을 검토하되 fence로 사용 중 영역을 보호한다.
  persistent mapping만 켜고 GPU가 읽는 영역을 덮어쓰거나 매 프레임 `glFinish`로 기다리지 않는다.
  밉을 늦게 업로드하더라도 이미 예약한 GPU 저장소 전체를 VRAM 예산에 계산한다.
  셰이더 소스/기능 버전·GPU/드라이버별 컴파일 캐시를 검증하고 잘못된 캐시는 재생성한다.

### 아트·기존 제작 기준

SF 개척 문명, 신비로운 표면과 깊어질수록 어두운 코스믹 호러를 유지한다. 고정 45도 쿼터뷰의
실제 화면 크기에서 실루엣·이동/상호작용 판독을 우선한다. 방향성 조명·그림자·블룸을 BaseColor에 굽지 않는다.
발광은 면적과 강도를 절제하고, 도장/소재/오염은 타입과 별도로 조정한다. 한글 안내는 동적 문구와 분리한다.
작은 홈·나사·봉제 디테일은 가능한 경우 공유 텍스처/노멀/트림으로 표현하되 실루엣·통행·가동부는 메시로 유지한다.
원본 디테일 보존 → 불필요 면 정리 → 규모별 폴리곤 예산 적용(기존 v3 유지 파츠 최대 200삼각형 / 신규·CQ-11 v4 파츠는 7절 규모별 LOD0~2 및 그림자 프록시 기준) 순서는 변경하지 않는다.

## 2. 채택할 조립·공유 구조

**제작은 모듈형 파츠/프리팹, 배포는 공유 자산과 필요한 정적 결합을 혼합한 구조로 한다.**
파츠마다 별도 드로우를 강제하거나 모든 조합을 완성 GLB로 굽는 방식을 기본으로 삼지 않는다.
프리팹은 조립 설명이며 한 프리팹이 한 드로우 콜이라는 뜻이 아니다.

```text
원본 파츠 + 재질/이미지 원본 + 리그/클립 + 프리팹 조립 설명
  → 오프라인 검증·중복 제거·의존성 분석·선택적 정적 결합
  → 공유 Mesh / MaterialTemplate / TextureSet / AnimationBank + Prefab
  → Scene의 Actor 인스턴스(위치·색·상태·소켓 부착) → RenderQueue
```

| 단위 | 소유할 정보 | 공유/변형 규칙 |
|---|---|---|
| Mesh / Part | 불변 정점·인덱스·UV·탄젠트·LOD·재질 슬롯·렌더 bounds | 색·오염·배치 위치를 메시 캐시 키에 넣지 않음. UV seam/하드 법선/탄젠트 handedness/재질 경계의 정점 분리는 보존 |
| MaterialTemplate | 셰이더 기능·채널 해석·alpha/cull/depth/shadow 규칙·텍스처 세트 참조 | 불투명/마스크/반투명은 실제 렌더 상태에 맞게 분리. 이미지별/색별 셰이더 복제 금지 |
| MaterialInstance | tint·거칠기/금속 보정·발광 강도·오염/손상 계수 | 같은 텍스처와 템플릿을 참조하는 작은 파라미터. 가능한 값은 인스턴스 속성으로 전달해 색 변경으로 배치를 깨지 않음 |
| Prefab / Recipe | 파트 ID·부모·local transform·재질 슬롯 바인딩·소켓/가동부·변형 허용 범위 | 실제 배치 Actor와 분리. 타입·색·장비 조합을 전부 파일로 열거하지 않고 검증된 선택 슬롯/프리셋을 사용 |
| AnimationBank | 리그/바인드 식별자·공유 클립·본 로컬 표본·마스크/이벤트 | 체형/의복/헤어별 같은 클립 복제 금지. 기존 23본·위상·스킨·실제 게임의 이동 소유권 보존 |
| SpatialChunk | 정적 배치 묶음·자식 참조·가림/LOD 범위·필요 자산 목록 | 도시 전체를 하나로 합치지 않고 Scene Graph의 가림/거리/로딩 단위를 유지. 충돌·진행 상태는 Actor/Scene이 소유 |

### 어떤 것을 합치고 남길지

1. 변하지 않는 한 건물의 외벽/기초/지붕 등은 동일 패스·머터리얼 계열·LOD·그림자 상태별로
   오프라인 결합할 수 있다. 공간 셀은 우선 16~32m를 비교할 시작값으로 두고 장면별 실측으로 결정한다.
   제작 원본의 파트를 없애거나 도시 전체를 합쳐 가림/출입구/스트리밍을 무력화하지 않는다.
2. 반복 기둥·가로 설비·도로 모듈·프롭은 동일 Mesh/MaterialTemplate을 공유하고 인스턴싱 후보로 남긴다.
   배치마다 정점을 복사하는 결합보다 전송량/드로우/가림 비용을 함께 비교한다. 모든 색/건물 조합의 완성 메시를 캐싱하지 않는다.
3. 문·가동 패널·바퀴·추진기·장비 부착·파괴/소실 가능 파츠와 투명 표면은 필요한 독립 제어를 유지한다.
   Actor/Scene Graph의 의미상 부모·소켓과 최적화된 렌더 묶음의 대응표를 납품한다.
4. 인물은 공통 리그·재질군 기준의 스킨 메시와 별도 헤어/장비 슬롯을 사용한다. 가려진 파트 제거는
   장비 조합과 가동 시 노출을 대조한 뒤 수행한다. 서로 다른 포즈의 NPC가 현재 경로에서 자동으로 한 번에 그려진다고 가정하지 않는다.
5. 결합/인스턴싱의 호환 키에는 패스·셰이더 기능·텍스처 페이지/샘플러·alpha/cull/depth·스킨/포즈·LOD·그림자 상태를 넣는다.
   불투명은 상태 정렬, 반투명은 필요한 깊이 순서를 보존한다. 드로우 수만 줄이려고 투명 순서/피킹/실제 가림을 깨지 않는다.
   가동/스킨의 최대 범위와 효과 bounds, 그림자가 수신면에 영향을 주는 범위를 별도로 검수한다.
   본체가 화면 밖이라는 이유만으로 Actor 수명을 끝내거나 아직 보이는 그림자를 갑자기 제거하지 않는다.

## 3. 텍스처·머터리얼 제작 규격

### 공유 표면과 페이지

- 반복 바닥·암벽·도로는 타일형 텍스처, 건물/기계 모서리·패널은 공통 trim sheet,
  작은 고유 표시/소품은 그룹별 atlas, 얼굴 등 고유 디테일은 필요한 전용 UV 영역을 사용한다.
  바닥/도로 반복 UV를 작은 atlas 셀에 그대로 반복시켜 이웃 영역을 읽지 않게 한다.
- 금속/외벽·노면·광산·인물 등 사용 장소·상주 수명·셰이더 기능이 비슷한 자산끼리 공유한다.
  전 세계 단일 atlas나 파트/색/도시마다 별도 4K 세트를 기본으로 하지 않는다. UI·글꼴 atlas는 별도다.
- 첫 검토는 공유 페이지 1024 또는 2048, 작은 프롭의 필요한 영역 256~512 수준에서 시작한다.
  월드 표면은 우선 128 texel/m, 플레이어/근접 인물은 256 texel/m를 검토 시작값으로 기록한다.
  화면 투영 크기·줌·저해상도 모드에서 근거가 있을 때 조정하고, 물체가 크다는 이유만으로 해상도를 올리지 않는다.
- atlas 영역은 전 채널의 배치·UV를 맞추고 경계 색 확장·밉 레벨별 패딩을 생성한다.
  회전/미러 패킹은 탄젠트 공간까지 검증하며 노멀 맵을 일반 컬러 이미지처럼 회전만 시켜 적용하지 않는다.
  고정 2px 여백이나 UV clamp만으로 모든 밉/이방성 필터의 번짐을 막았다고 하지 않는다.
  타일형은 wrap 경계가 이어지게 제작하고 거친 밉에서 trim/작은 표식이 소실·오염되지 않는지 검수한다.
- 같은 크기·포맷·밉 구성의 표면군에는 새 렌더러의 texture array를 우선 사용한다.
  크기/포맷/상주 수명이 다른 자산은 별도 배열/2D 페이지로 구분하고 레이어 ID는 인스턴스 데이터로 전달한다.
  모든 이미지를 가장 큰 레이어 크기에 맞춰 늘려 메모리를 낭비하지 않는다.
  bindless·가상 텍스처·런타임 모든 조합 재베이크는 초기 필수 조건으로 삼지 않는다.

### 맵별 채널·색 공간

| 맵 | 제작/해석 계약 | 선택 기준 |
|---|---|---|
| BaseColor | RGB sRGB, alpha는 coverage/opacity 데이터. tint 가능 영역은 중립색/명도와 공유 마스크로 분리 | 직접광/그림자/블룸을 굽지 않음. 알파가 필요 없는 표면은 불투명으로 명시 |
| Normal | 선형 데이터, tangent-space +Y 기준, 탄젠트 방향/handedness를 명시 | UV·미러 변환·법선과 함께 검수. 색 보정/sRGB 디코딩 금지 |
| ORM | 선형 R=AO, G=roughness, B=metallic. AO와 MR은 각각 올바른 glTF 슬롯에서 같은 이미지/UV를 참조 | 밀도·UV·샘플러가 호환될 때만 채널 결합. 서로 다른 용도의 alpha를 무조건 한 채널에 겹치지 않음 |
| Emissive | RGB sRGB 원본, 강도/색 보정은 선형 파라미터 | 발광 면이 없는 자산은 생략. 별도 대형 발광 이미지보다 공유 마스크/영역을 우선 |
| Tint/오염/손상/효과 마스크 | 선형 데이터. 채널별 의미·범위·기본값을 명시 | 색만 다른 같은 타입의 메시/컬러 맵 복제 금지. 추가 샘플 비용이 이득보다 크면 단순 파라미터 사용 |

공유 기본값은 흰 BaseColor, 평면 Normal, AO=1/roughness=1/metallic=0, Emissive=0이다.
없는 맵마다 새 이미지를 만들지 않고 상수/공유 기본 텍스처를 쓴다. 최종 표시의 sRGB 변환은 한 번만 적용한다.
ORM/노멀과 BaseColor는 같은 색 공간으로 뭉쳐 필터링하지 않는다. 거칠기/노멀의 밉 생성은 데이터 의미를 보존한다.
투명은 `opaque / mask / blend`, cutoff, 양면 여부, 그림자 방식을 명시한다. 가능한 헤어/식생은 mask를 검토하고,
전체 유리/홀로그램을 불투명과 합치지 않는다. mask는 본체·그림자에 같은 coverage 기준을 사용한다.

### UV·탄젠트·저장 형식

- 미터 단위와 기존 authoring/glTF 축 변환을 정확히 한 번 적용한다. UV 원점/이미지 행 방향,
  `TEXCOORD_0`/필요한 추가 UV, tangent.w, 미러 handedness를 계약에 기록한다.
  노멀 맵을 추가하려고 원본을 재중앙화하거나 조립 좌표/바인드/충돌을 변경하지 않는다.
- 이미지 원본은 편집 원본과 무손실 내보내기를 보존한다. GLB마다 같은 이미지를 중복 내장한 경우
  배포 팩에서 이미지 콘텐츠 해시로 한 번만 보관한다. 경로가 달라도 동일한 이미지/해석은 공유할 수 있다.
- GPU 배포는 오프라인 밉/압축 생성과 KTX2 같은 밉 포함 컨테이너를 검토한다. 컨테이너와 GPU 압축 포맷은 다르다.
  새 OpenGL 프로필에서 BC7 등 색 맵·BC5 노멀을 검토하고, 검수/지원 프로필에 맞는 포맷을 선택한다.
  BC5 사용 시 XY 복원/정규화 경로까지 명시한다. 현 엔진이 BC7/KTX2를 읽는다고 가정하지 않는다.
  런타임 PNG 디코딩/밉 생성/포맷 변환을 매 프레임 반복하지 않으며 시작 시 트랜스코딩 비용도 측정한다.

## 4. 캐시·로딩·메모리 설계 요구

1. `asset_id / part_id / prefab_id / material_id / texture_set_id / rig_id`는 안정적인 논리 ID다.
   파일 열거 순서·파일 경로·GPU 번호를 영구 ID로 쓰지 않는다. ID와 변경 내용의 해시를 분리하고
   중복 ID·의존성 순환·없는 슬롯·잘못된 조립 변환은 검증 실패로 보고한다.
2. 빌드 캐시는 메시(정점/UV/LOD/가공 옵션), 이미지(픽셀/색 공간/압축/밉), 재질(셰이더/바인딩),
   프리팹(파트/변환/선택 규칙)을 별도 콘텐츠 키로 관리한다. 텍스처 색 수정으로 스킨/본/지형까지 다시 만들지 않는다.
   반대로 외부 PNG·재질 JSON·조립/압축 설정 변경을 GLB 파일 해시만으로 놓치지 않는다.
   전체 입력 의존성 그래프·도구 버전·출력 해시·역의존성·결정적인 정렬을 manifest에 남긴다.
3. 전체 조합을 미리 생성하지 않고 실제 납품 프리셋/배치에서 쓰는 결합만 준비한다.
   기초 공용 팩 + 자산군/지역별 의존성 청크 + 작은 인덱스를 목표로 하며 지역 팩에 공용 텍스처를 중복 복사하지 않는다.
   단일 v3 팩의 즉시 분할/삭제를 뜻하지 않으며 전환 전후의 시작 시간·증분 빌드·디스크 크기를 비교한다.
4. AssetManager의 중앙 핸들/참조/세대 번호로 동일 자원의 동시 로드 요청을 합친다.
   CPU 디코딩/검증은 작업 스레드, GPU 생성/업로드/삭제는 기존 GL 컨텍스트 소유 스레드에서 수행한다.
   프레임/큐가 참조 중인 GPU 자산을 즉시 삭제하지 않고 안전한 프레임 경계와 핸들 갱신을 사용한다.
5. 상시 공용 자원과 현재/인접 공간의 자원을 구분한다. 텍스처는 항목 수가 아닌 실제 할당 바이트·밉/포맷으로
   예산을 관리하고 LRU는 현재 참조/고정 자원을 함부로 해제하지 않는다. 초과 시 먼 자산/고해상도 밉부터
   조정하며 완성되지 않은 텍스처를 화면에 공개하지 않는다. 파일/최고 해상도 요청을 화면 밖까지 한꺼번에 올리지 않는다.
6. 검토 시작값: 월드 텍스처 상주 예산은 낮음 128MiB / 높음 512MiB, CPU 업로드 대기는 64MiB,
   플레이 중 업로드는 프레임당 2MiB와 CPU 준비/발행 약 1ms를 예산으로 계측한다.
   이는 장비별 조정할 설계값이며 성능 보장이 아니다. 큰 이미지/압축 블록은 복수 프레임·밉 단위로 나누고,
   GL 업로드의 실제 정지 시간도 별도 측정한다. 시작 로딩 예산과 플레이 중 예산은 구분한다.
7. 메모리 계산 예: 2048² RGBA8 한 장은 기본 레벨 16MiB, 전체 밉은 약 21.33MiB다.
   BaseColor/Normal/ORM 세 장은 약 64MiB이며 발광·staging·중복 버퍼는 별도다.
   디스크 PNG 용량을 VRAM으로 보고하지 않는다. 렌더 타깃·그림자·UI/글꼴·메시·애니메이션은 위 월드 텍스처 예산과 별도로 합산한다.

## 5. 납품 메타데이터와 검수 기준

다음 항목은 **새 납품 계약의 논리 필드**다. 현재 JSON/바이너리 로더가 이미 파싱한다는 뜻이 아니다.
기존 schema를 몰래 바꾸지 말고 스키마/변환기 버전·기능 플래그와 명시적인 마이그레이션을 제공한다.

| 분류 | 필수 기록 |
|---|---|
| 출처 | 안정 ID·원본 경로/라이선스·schema/version·내용 해시·도구/빌드 옵션·의존성 ID |
| 메시 | 미터 단위/축·파트 원형·변환/법선/UV/탄젠트 규약·정점/인덱스/서브메시 수·LOD·가동/결합 허용·리그/소켓 |
| 재질/이미지 | 템플릿/슬롯·texture_set·맵별 색 공간/포맷/채널·크기/밉·sampler/wrap·alpha/cull/shadow·기본값 |
| 프리팹 | 부모/자식 파트 ID·local transform·재질 override·가동/장비 선택·렌더 결합과 의미 노드의 대응 |
| 공간/접속 | 렌더 bounds와 충돌 envelope 분리·출입구/보행/차량 포트·바닥/기초 접지·스트리밍 그룹 |
| 비용/상태 | 원본/결과 삼각형·재질/투명 슬롯·참조/고유 이미지 수·예상 상주/업로드 바이트·결합/인스턴싱 예상 그룹·제작/연결/검수 상태 |

- 첫 시범의 불투명 재질 슬롯 목표는 정적 모듈/차량 2개 이하, 기본 인물 3개 이하로 둔다.
  유리·헤어·부착물은 별도 사유/비용을 기록한다. 예산을 맞추려고 파트를 늘리거나 중요한 소재 구분을 지우지 않는다.
  최종 드로우는 LOD·공간·스킨/포즈·그림자 패스마다 달라지므로 슬롯 수와 함께 실측한다.
- 원본/텍스처 적용/최적화 결과를 같은 카메라·조명·노출·줌에서 비교한다.
  seam/밉 번짐·노멀 반전·반복 밀도·발광 과다·헤어/유리 정렬·그림자 coverage·접지·가동 시 관통을 검수한다.
  밝은 도시·어두운 광산·곡선/경사 도로·NPC 군집·차량/비행체·최저/최고 화면 해상도를 포함한다.
- 게임 통합 후 성능 보고는 CPU p50/p95·GPU pass 시간·FPS와 함께
  `resource_mesh_unique_count`, `resource_mesh_instance_count`, `resource_mesh_dedup_ratio`,
  `material_template_count`, `material_instance_count`, `material_batch_breaks`, `texture_unique_count`,
  `texture_resident_bytes`, `texture_staging_bytes`, `texture_upload_bytes`, `texture_upload_cpu_ms`,
  `texture_cache_hits/misses/evictions`, `resource_io_ms/decode_ms`, `resource_dependency_rebuild_count`를 제안한다.
  기존 같은 의미의 로그는 재사용하고 새 이름은 통합 시 단위/표본 구간/고유 수 기준을 확정한다.
  이 문서만으로 해당 새 로그가 이미 구현되었다고 표시하지 않는다.
- **수용 기준:** 외형·UV·기존 충돌/접속/진행 지문을 보존하고, 색만 다른 배치가 메시/이미지를 복제하지 않으며,
  한 공유 PNG 변경이 관련 자원만 무효화해야 한다. 지역 왕복 뒤 상주/업로드 대기 메모리가 안정되어야 한다.
  같은 장면의 드로우·상태 전환·시작/프레임 시간·VRAM을 기존 방식과 비교하고 악화 시 원인을 기록한다.
  목표 기기 60FPS 검증과 제작 도구 미리보기 통과는 별도다. 게임 빌드/실행 검수는 사용자가 수행한다.

## 6. 적용 순서와 책임

1. 제작 담당: 기존 자산/맵/재질 슬롯 목록과 시범 세트의 UV·재질/공유·비용표를 먼저 납품한다.
2. 제작·통합 담당: 논리 ID/재질 슬롯/텍스처/리그/조립 스키마와 미지원 기능 처리 정책을 합의하고 시범 세트를 고정한다.
3. 통합 담당: 팩/로더에 인덱스·UV/탄젠트·서브메시·텍스처 참조를 추가하고 새 버전을 명시적으로 검증한다.
   v3/정점색 경로의 유지 또는 변환 방식을 정하고 불완전한 새 팩을 성공으로 취급하지 않는다.
4. 통합 담당: 새 컨텍스트/GLSL·정점/버퍼/패스 계약과 색 공간·텍스처 샘플링·인스턴스 재질 파라미터·alpha/그림자·캐시/예산 업로드를 연결한다.
   기본 컬러 연결을 검수한 뒤 Normal/ORM/Emissive를 순차 활성화하고 카툰/저해상도 모드를 유지한다.
5. 제작 담당: 검수된 공유 규격을 다른 자산에 확장한다. 통합 담당은 정적 결합/인스턴싱/LOD/지역 청크를 실측에 따라 적용한다.
   Blender 담당이 게임 코드·`Resource/Runtime`을 함께 수정하거나 전체 자산을 먼저 일괄 재패킹하지 않는다.

기술 해석은 [glTF 2.0의 재질·텍스처 규격](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#materials),
[KTX2 컨테이너 규격](https://registry.khronos.org/KTX/specs/2.0/ktxspec.v2.html),
[OpenGL 4.5 Core](https://registry.khronos.org/OpenGL/specs/gl/glspec45.core.pdf),
[GLSL 4.50](https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.4.50.pdf)와
[최신 OpenGL/GLSL 레지스트리](https://registry.khronos.org/OpenGL/index_gl.php)를 확인했다.
공유 구조·페이지 크기·재질/메모리/업로드 예산은 이 프로젝트를 위한 설계 선택이며 업계 공통 상한이 아니다.

  둘지는 메타데이터에 명확히 기록하여 이중 오프셋을 방지한다.
- 접속 포트·실측 크기·법선·UV·재질, 지상/고가 level, 램프 경사·높이, 회전 경로·보행 여유를 보존한다.

## 애니메이션 납품 계약

- 현재 23본·부모 순서·바인드·스킨·총구·발 접지·기존 전체 클립을 유지한다. 후진/옆걸음/권총 운반/재장전은
  이미 존재하므로 성능 리팩토링을 이유로 중복 제작하지 않는다.
- 새 모션은 클립명, duration, loop 여부, 기본 이동/상체/전신 구분, 참조할 블렌드 표본·마스크를 명시한다.
  런타임 이동·yaw·피격 판정은 게임이 소유하며 클립 root motion으로 바꾸지 않는다.
- 같은 리그·바인드·애니메이션을 쓰는 체형/의복/헤어는 공유 뱅크로 묶일 수 있게 식별 계약을 유지한다.
  미사용 클립을 원본에서 삭제하지 않는다. 클라이언트는 실제 연결된 그래프의 로컬 본 표본만 시작 때 준비한다.
- 향후 오프라인 로컬 TRS 표본 납품을 채택하면 이름/부모/바인드/표본 시간/쿼터니언 규약과 역변환 비교를 제공한다.
  현재 v3 바이너리 변경과 pack 도구 수정은 클라이언트 담당 영역이며 이번 요청만으로 바꾸지 않는다.

리소스 원본·내보내기·검증 자료는 Resource 안에 보관하고, 게임 코드/Runtime 캐시를 모델링 작업에서 수정하지 않는다.

## CQ-01E 후속 — 도시/지대별 실측 건물 메시 제작 요청 (2026-11-02)

사용자 확정 사항: **기존 건물을 늘이거나 줄여 다른 크기/용도로 사용하는 것은 현재 테스트 단계에서만 허용한다. 정식 콘텐츠에서는 용도·규모에 맞는 새 건물 메시가 필요하다.** 이번 요청은 제작 대기이며 기존 리소스 교체나 폴리곤 감축을 바로 수행하라는 지시가 아니다.

- 시내의 소규모 주거·상점/정비소·의료소, 소도시의 물류/대중교통·시장, 대도시의 복합 주거/행정·상업, 항성계 수도의 관문 행정/대형 공공 건물을 서로 다른 실루엣과 실제 층고·출입 구조로 제작한다. 개척지의 작업장·운송 시설·폐설비와 광산의 출입/지원동도 별도 목적에 맞춘다.
- 런타임에서 기존 창문·문·층고 전체를 비균일 스케일로 늘여 대형 건물을 만드는 납품은 금지한다. 높이/폭의 변형이 필요하면 실제 층·동·중정·설비/보행 접속을 설계한 크기별 모델 또는 제작 의도가 있는 모듈 조립 구성을 제공한다. 같은 물건의 복제 배치·방향 회전은 허용한다.
- +X 전방·+Y 측면·+Z 위, 미터 단위, 기존 원점/조립 계약을 따른다. 플레이어 1.8m, 게임 1월드 단위=2m를 기준으로 문/계단/보행 폭/차량 진입부를 실측한다. 도시 배치의 기본 축은 헤일로와 같고 고정 쿼터뷰에서 45도로 보인다. 임의의 보정 회전이나 재중앙화를 메시 안에 굽지 않는다.
- asset_id별 실제 크기, 지면 피벗, 출입구/차량 입구·보행 접속점, 권장 대지/도로 후퇴선, 충돌 envelope와 지붕/외벽 가림 구분을 명시한다. 렌더 bounds 전체를 보행 충돌로 쓰지 않아도 되도록 실제 통행 가능한 공간을 제공한다.
- 공통 카툰 렌더 재질과 SF 개척 문명 콘셉트를 유지한다. 상세 원본을 먼저 제작하고 [제작 지침](AGENTS.md)의 버전별 예산·토폴로지 정리·한도 우회 분할 금지를 따른다. 기존 v3 호환본에는 최대 200삼각형의 파트별 예산을, 신규 v4 건물에는 7.2절 파트·조립체 예산과 R2 납품 기준을 적용한다.
- 납품 시 원본/최적화본·조립 메타데이터·실측 치수·45도 쿼터뷰 및 출입구/차량 접근 비교를 제공한다. 클라이언트는 새 asset_id·실측 크기/출입 계약을 연결한 뒤 현재 `ContentLayout`/`DrawSurfaceStructure`의 테스트용 메시 크기 맞춤 경로를 교체한다. 현재 스케일 맞춤 경로를 정식 자산 계약으로 확정하지 않는다.

## CQ-02A 후속 — 건물 바닥·기초·지형 접지 계약 보충 (2026-11-03)

**요청 상태:** 기존 건물을 삭제하거나 재제작하는 지시가 아니라, CQ-01E의 실측 크기 건물 납품에 필요한 접지 메타데이터 보충이다. 원본은 먼저 정밀하게 제작하고 기존 파트별 삼각형 예산을 지킨다.

- 건물별로 미터 단위 `ground_contact_z_m`(지면 기준), `floor_surface_z_m`(보이는 바닥), 기초/스커트 유무·깊이, 수평 바닥 범위, 출입구 문턱·계단/경사로 높이, 충돌 범위와 실제 피벗을 제공한다. 이것들은 **납품할 정보 항목**이며 현재 로더가 이 필드 이름들을 자동 파싱한다는 뜻은 아니다.
- 지형을 덮는 바닥판·기초 상판을 동일한 Z에 중복 배치하지 않는다. 메시 안에 두 겹의 공면 바닥이 있으면 원본에서 정리한다. 표식/장식은 의도된 별도 높이 또는 재질 표현으로 구분하고, 엔진의 깊이 검사를 끄거나 과도한 depth bias를 전제로 납품하지 않는다.
- 경사지용 기초/스커트는 불투명 측면으로 지형까지 이어져 공중에 뜬 틈이 보이지 않게 한다. 지면 기준을 바꾸기 위한 임의 재중앙화·전체 메시 축 변환은 하지 않는다. 지하실이나 실제 출입구는 자동 기초 상자로 막지 않도록 개구부 범위를 함께 명시한다.
- 현재 테스트 렌더는 건물 하단을 기준 지면보다 0.08m 올리고 기초 상판을 0.10m에 두어 0.02m 겹쳐 접지한다. 충돌체·도로 접속 높이를 같이 올리지 않는다. 새 배치는 대지 5×5 표본의 최고 높이를 기준으로 한다. 이 임시 수치를 원본 메시에도 중복으로 굽지 않는다. 새 접지 계약을 로더에 연결할 때 자산별 지면/바닥·개구부를 사용하고 테스트 보정을 대체해야 한다.
- 45도 쿼터뷰에서 정지·이동/줌, 평지·완만한 경사, 가까운 보도/도로, 낮은 태양/그림자 장면을 비교한다. 바닥 격자 깜빡임, 노출된 틈, 문턱/플레이어 1.8m 스케일, 저해상도 모드 판독을 검수한다. 게임 빌드·GPU/FPS 검증은 별도다.
